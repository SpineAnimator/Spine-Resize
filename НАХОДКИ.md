## 1. .skel — уже разобран, roundtrip байт-в-байт

Файл: `src/lib/spineSkel.ts` (копия `recovered-spine/spineSkel.ts`).

Проверка:

```bash
node --experimental-strip-types -e '
import { readFileSync } from "fs";
import { readSkel, writeSkel } from "./src/lib/spineSkel.ts";
const b = new Uint8Array(readFileSync("recovered-spine/gunslinger.skel"));
const out = writeSkel(readSkel(b), 1);
let d=0; for (let i=0;i<b.length;i++) if (out[i]!==b[i]) d++;
console.log(d===0 ? "roundtrip ok" : "DIFF "+d, b.length);
'
```

Ожидание: `roundtrip ok 30283`.

Формат как Esoteric `SkeletonBinary` 4.2/4.3.

Что читается структурно:

- hash (2× int32), version, bounds x/y/width/height, referenceScale, nonessential
- таблица строк, кости (parent = индекс), слоты (пока сырые байты), ограничения, скины, события, анимации
- кости: name, parent, rotation, x, y, scaleX, scaleY, shearX, shearY, inherit, length
- вложения region/mesh/bbox/linked/path/point/clip
- костные таймлайны анимации (translate/scale/shear/rotate/inherit)

Поле `Flt.k`:

- `k = 1` — дистанция, её надо умножать при ресайзе
- `k = 0` — угол, масштаб, вес, время, uv

Уже помечены `k=1`: bone x/y/length, region x/y/width/height, вершины меша (у взвешенного третий float — вес, `k=0`), path lengths, point x/y, translate-ключи (не scale/rotate/shear), IK softness, path position/spacing когда режим в единицах длины, bounds width/height.

Не помечены, хотя это тоже дистанции (баг, поправить при ресайзе):

- skeleton bounds `x` и `y` читаются с `k=0`. Надо масштабировать.
- `referenceScale` и `fps` масштабировать **нельзя**.

Слоты, события, ik/transform/path/physics/slider/deform/drawOrder в анимации пишутся сырыми байтами. Translate костей масштабируется. Deform-вершины пока нет.

`scaleSkel(sk, factor)` умножает все `k=1` и ставит `k=0`, чтобы `writeSkel` не умножил второй раз. Нельзя вызывать и `scaleSkel`, и `writeSkel(..., factor)` вместе.

Порядок кривых (уже починен, из-за этого roundtrip раньше расходился на 3288 байт с offset 24041):

```
time0, values0,
time1, values1, curve0, [bezier],
time2, values2, curve1, [bezier],
… последний ключ без curve
```

### Bake scale — правильный алгоритм (ещё НЕ в коде)

В `app.js` bake **неверный**. Он умножает локальные x/y/length кости на **её собственный** scale и ставит scale=1. Собственный scale не двигает origin кости: он увеличивает детей, длину и вложения. У `Ch_frame_light` y=2.5 и scaleY=7.23 старый bake утащит кость в y=18 и сожмёт картинку.

Правильно, от корня к листьям, inherit = normal (0), без shear:

1. `sx, sy` = текущий scale кости.
2. `length *= sx` (длина вдоль локальной X).
3. Вложения слотов, привязанных к этой кости: x*=sx, y*=sy, width*=sx, height*=sy, вершины меша так же. Свой scale вложения не трогать.
4. Детям: `child.x *= sx`, `child.y *= sy`, `child.scaleX *= sx`, `child.scaleY *= sy`.
5. Translate-ключи ребёнка умножить так же. Scale-ключи ребёнка умножить на sx/sy (они абсолютные).
6. Scale-ключи самой кости разделить на старый sx/sy (setup станет 1, анимация сохранит отношение).
7. Поставить scale кости = 1 и идти дальше. Дети получат составной scale и запекутся на своём шаге.

Если inherit не normal (`noScale`, `onlyTranslation`, …), шаг 4 нельзя делать вслепую: чужой scale на ребёнка не проходит.

Неравномерный scale родителя + повёрнутый ребёнок нельзя честно записать в scaleX/scaleY без shear. Для равномерного scale (gun-a) ошибка нулевая.

Слот в сырых байтах, индекс кости достаётся так: string (varint длины, 0 = null, иначе длина-1 и байты), сразу следом varint индекса кости. Дальше цвет и прочее не нужны.

Deform в анимации — сырой блок. Вершины ключа надо умножать, bezier кривой (4 float на кадр) лучше не трогать: это одна кривая на весь ключ, не позиции вершин. После патча обязателен тест: factor=1 даёт те же байты, factor≠1 файл снова читается `readSkel` до конца.

Потом общий множитель «вписать в квадрат»: AABB setup-позы → factor = target / max(width, height) → `scaleSkel`. Картинки и atlas тем же factor.

## 2. .spine — проект редактора, raw deflate

`symbols.spine` 23353 байт. Это **не** zlib-обёртка и не zip.

Первые байты файла: `ec bd 07 58 …` — сырой deflate.

```python
import zlib
raw = open("recovered-spine/symbols.spine","rb").read()
data = zlib.decompress(raw, -15)   # wbits=-15 = raw deflate
# len(data) == 60511
```

`zlib.decompress(raw)` и gzip падают. Обратно писать тоже raw deflate (`wbits=-15`). Сжатие не детерминировано: сравнивать надо распакованные байты. При factor=1 распакованный буфер обязан совпасть с оригиналом.

Внутри в начале строка версии редактора `4.3.2` (не 4.3.26 — это версия экспорта json/skel).

### Строки

Не length-prefix. Поток байтов `< 0x80`, последний байт `>= 0x80`, младшие 7 бит — последний символ.

`68 61 6e 64 2d 6c 65 66 74 2d 63 6f 6e 74 72 6f ec` = `hand-left-control` (`ec & 0x7f = 'l'`).

Так же обрезаются `gunslinger`, `hip`, `Ch_cherry`.

### Подпись кости

Сразу после имени 8 байт, 71 раз:

`21 3F 80 00 00 02 01 1E`

Это маркер записи кости, не родитель.

### Хвост кости — совпал со всеми 70 костями JSON

Жёсткий якорь, по которому нашлись **все 70** костей экспорта плюс редакторская `cherry-size` (в json её нет):

```
0A  <float32 BE x>
22  00 00 00 00
0E  <float32 BE scaleY>
1F 0F 01 00
09  <float32 BE length>
1B  15 1D 00          или  1B 01 01 1D 00
0B  <float32 BE y>
01 01
<имя, high-bit>
21 3F 80 00 00 02 01 1E
```

Перед `0A` (проверено на hip / spine / root / Ch_frame_light / GS_gilza):

```
0D  <float32 scaleX>
0C  <float32 rotation>
17  00 00 00 00
1C  <байт типа: 13 обычная, 18 control, 01/74/98 с иконкой>
    [опционально строка иконки: "bone", "ik", …]
0A  …
```

Сверка с json, допуск 0.05 / 0.02 на scale:

- hip: x=61.192 y=-357.36 rot=0 len=0 scale=1
- spine: x=-1.501 y=0 rot=83.029 len=202.514
- tors: x=202.514 (это length родителя spine, не путать) rot=14.525 len=234.724
- Ch_frame_light: scaleY тег `0E` = 7.228224, scaleX тег `0D` = 1
- GS_gilza: `0D` ≈ 1.227, `0E` ≈ 1.239
- root и hand-left-control тоже находятся, если между `1C` и `0A` разрешить строку иконки. Первый узкий regex без иконки их пропускал (63 из 71). Якорь `22 00 00 00 00 0E` ловит все 71.

Что масштабировать у кости: **только** `0A` (x), `0B` (y), `09` (length).

Не трогать: `0C` rotation, `0D` scaleX, `0E` scaleY, константы `17/22/1F 0F 01 00/1B …/01 01`, подпись `21 3F 80…`.

Одинаковые теги в других местах файла значат другое. Нельзя умножать каждый `0A/0B/09` в файле. Только внутри этого хвоста.

Порядок костей в `.spine` ≠ порядок в json. Пример: в проекте сразу после root идёт `hand-left-control`, в json второй — `gunslinger`.

### Родитель в .spine не найден

Искали байт-индекс сразу после подписи. Там стабильно `01 7E 00/01 …`, это не parent.

Равномерный масштаб всех local x/y/length всё равно масштабирует мир: каждая трансляция линейна, scale родителя остаётся множителем. Для «вписать в квадрат» дерево не нужно.

Для bake чужого scale≠1 дерево нужно. Пока родителя в бинаре нет — **bake scale=1 для .spine не делать**. Иначе поза разъедется. Равномерный scale дистанций — да.

### Регион (не меш) — 7 из 7

В json регионов с width/height и без type=mesh ровно 7 (`Ch_cherry`, glow, line, orn, square, …). Все нашлись.

```
0C  <float32 height>     # 195 у Ch_cherry
07  <float32 y>          # 4.782
06  <float32 x>          # 4.035
0F 00 0E 1E 01 FF FF FF FF
09  <float32 ~1>         # множитель, НЕ масштаб дистанции
0B  <float32 width>      # 204
0D 0A 01 01
<имя вложения>
```

Масштабировать: x, y, width, height. Тег `09` между ними не трогать.

Теги `0C/0B` здесь высота/ширина, а в кости `0C` = поворот и `0B` = y. Контекст обязателен.

### Меши

62 меша. Делятся так (json):

- **невзвешенные** — `len(vertices) == len(uvs)`, пары x,y. Таких мешей 6, точек 24. Пример `GS_card-20`: `[78.46, -140.25, -47.06, -140.25, …]`, uvs `[1,1, 0,1, 0,0, 1,0]`.
- **взвешенные** — 56 мешей. На каждую вершину: `boneCount`, потом `boneCount` раз `(boneIndex, x, y, weight)`. Пример `Ch_frame_light` (4 вершины, uvs 8 чисел, vertices 20 чисел):

```
(bone 69, x 2.06, y -17, w 1)
(bone 68, x -2.06, y -17, w 1)
(bone 68, x -2.06, y 17, w 1)
(bone 69, x 2.06, y 17, w 1)
```

Невзвешенная точка в бинаре (проверено на `GS_card-20` и `GS_glow`):

```
01 11 01 02  <x f32> <y f32>  36 01 02 00 11 01
```

Вокруг ещё float `1.0` (uv или вес). Масштабировать только x и y после `02`, и только если дальше ровно `36 01 02 00 11 01`. В файле таких записей больше, чем 24 json-точки (нашлось 106): часть — вторая копия блока, часть похожа на тот же шаблон. Слепое умножение всех 106 уменьшит и копии. Это, скорее всего, правильно (обе копии — те же координаты), но перед боем сверить multiset.

Взвешенный шаблон другой. Возле `Ch_frame_light` (offset ~3626):

```
01 11 01 04  <4 float BE>  36 01 02 00 11 01
```

Первая четвёрка: `[31.94, -17.0, 2.06, -17.0]`. В json у этой вершины x=2.06, y=-17. Они есть среди четырёх float, но не парой «индекс 0 = x, 1 = y». Таких групп `01 11 01 04` нашлось 72 — это мало на 56 мешей (у `GS_hand-j` одних вершин сотни). Значит большинство взвешенных вершин лежит в другом шаблоне, его ещё не зафиксировали.

Пока для .spine безопасно масштабировать:

1. хвосты костей (x, y, length) — 71 запись, сверено;
2. регионы (x, y, width, height) — 7 записей, сверено;
3. невзвешенные вершины по шаблону `01 11 01 02 … 36 01 02 00 11 01`.

Взвешенные меши (тело, руки, голова) без их шаблона **не уменьшатся**. Поза костей уменьшится, картинка меша останется большой. Это следующий кусок работы, не закрывать глаза.

Ширины меша в json (`width/height` у mesh, например 34 у `Ch_frame_light`, 1585×1134 у `GS_glow`) в бинаре лежат отдельно (float 34 находился, float 1585 — тег `10` рядом с `GS_glow` дал 1025, не 1585). Слепо умножать все теги `10/11` нельзя.

### Анимации .spine

Translate-ключи json (пары float) паттерном `00 + x + y + 01` раньше насчитались 149 раз против 104 ключей. Запас есть, вслепую не умножать. Deform в этом json нет. После масштабa костей анимационные translate останутся в старом размере — поза setup будет верной, клипы разъедутся. Искать ключи отдельно.

### Как вписать .spine в квадрат без дерева

Грубый AABB уже посчитан по json setup (регионы с поворотом):

- min (-791, -924), max (854, 679)
- 1645 × 1603
- в квадрат 300: factor ≈ 0.182

Для самого .spine AABB надо собирать из костей после world-transform. Без родителя world-transform не построить. Практичный путь, пока родителя нет:

- factor задаёт пользователь, либо
- сначала экспорт json/skel (там родители есть) считает AABB, тем же factor крошатся картинки и .spine.

Не выдумывать родителей из порядка имён.

## 3. Что делать следующим коммитом с кодом

1. `.skel`: слот → bone index, AABB, bake по алгоритму из §1, потом один `scaleSkel`. Deform патчить отдельно и проверить roundtrip.
2. Поправить bounds x/y (`k=1`). Не трогать referenceScale и fps.
3. `.spine`: inflate → масштаб только полей из §2 (кости, регионы, невзвешенный меш) → raw deflate. Тест factor=1: распакованные байты идентичны.
4. Картинки и atlas — тем же factor, что скелет.
5. UI: чёрный, один экран, мало текста, одна основная кнопка. Скелет json уже умеет старый `app.js`; bake в нём заменить на родитель→дети.
6. Не коммитить токен. Пушить в `SpineAnimator/Spine-Resize` ветку `main` (это же GitHub Pages).

## 5. Дописано после восстановления UI

Второй хвост вершин меша в `.spine`: `1f 1e 01 ff` (первый остаётся `36 01 02 00`).
С ним на symbols.spine нашлись и умножились все 809 ненулевых x взвешенных и невзвешенных вершин из gunslinger.json.
Повороты костей и scaleX/scaleY при этом не меняются: их смещения помечаются как locked.
Равномерный центр для `.spine` — прибавка к local x/y кости `root` (у gunslinger root без поворота, local = world).
